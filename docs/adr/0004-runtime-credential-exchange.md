# ADR 0004: Runtime credential exchange via QR + join token

Status: Accepted

## Context

`docs/technical-blueprint.md` §11 で「Unity mobile clientはモバイルデータ通信上で認証情報を入力し、APIからruntime token、manifest、signed asset URLを取得する」と決めている。だがHMD (Quest 3 / XREAL) でemail+passwordをvirtual keyboardで入力させるのは展示・出張デモ環境で破綻する。実装段階で具体的なauth flowを確定する必要がある。

並行する制約:

- `ManifestClient` は現状 unauthenticated で `/api/v1/runtime/{code}/manifest` を叩く。Production では Bearer 必須にしたい。
- Supabase Auth JWT を device に持たせるとSupabase service role / refresh policy / RLS の責任がclientに漏れる。
- `manifest.qa.runtimeToken` がすでに存在し、これはWebSocket QA用の短期tokenとして機能している (LiveQaSocket)。これと混同したくない。
- 一台のdeviceが複数sessionに参加する可能性 (workshop でA poster → B poster) があり、sessionごとにcredentialを分離保存できる必要がある。

## Decision

Unity client は **Supabase に直接話さない**。すべての認証情報は Chimera API 経由で受け渡す。

### Auth flow (HMD-friendly)

```text
1. Dashboard で session publish
   → server が join token 発行 (single-use, ~10 min)
   → poster QR / 配布QRに "chimera://session?code=<code>&join=<joinToken>" を埋め込む

2. Quest 3 / XREAL device:
   ISessionEntryProvider が QR scan or manual entry で SessionJoinToken を返す
   (Phase 0は ManualSessionEntry のみ。camera scannerは Phase 2/3 で gated 実装)

3. POST /api/v1/runtime/exchange
     body: { sessionCode, joinToken, deviceId, deviceLabel }
     200 : { runtimeToken (~15min), refreshToken (~12h), expiresAt, scope }
   joinToken はserver側で immediately invalidate (single-use)。

4. CredentialStore が PlayerPrefs に sessionCode-namespaced で保存
   key: "chimera.creds.<sessionCode>" → JSON of SessionCredentials

5. ManifestClient が "Authorization: Bearer <runtimeToken>" でmanifest取得
   401時:
     ChimeraSession が refreshToken で /runtime/refresh → 1回retry
     さらに失敗 → CredentialStore.Clear → OnAuthRequired → step 2 へ戻る

6. Asset download は manifest の signed URL を使う (Authorization header不要)。

7. LiveQaSocket は manifest.qa.runtimeToken (server側で別途mintされたWS用token) を使う。
   /runtime/exchange の runtimeToken とは別物として扱う。
```

### Token lifetimes (server-side契約)

| Token | Lifetime | Purpose | Storage |
|---|---|---|---|
| `joinToken` | ~10 min, single-use | QRから1回だけexchangeする | QRのみ。device保存しない |
| `runtimeToken` | ~15 min | manifest取得 / asset metadata | PlayerPrefs (短期、再発行可) |
| `refreshToken` | ~12 hours | 黙ってrefreshする | PlayerPrefs (P0)、Android Keystore (P1) |
| `qa.runtimeToken` | session有効期間 | LiveQaSocket WSS auth | manifest内のみ |
| signed URL token | 5-15 min, in URL | private asset DL | URLのみ |

### Why not Supabase SDK on device

- Supabase JWT は project全体にscopeが広がる。session scopedにできない。
- Supabase Auth UI を XR で出すのは現実的でない。
- token rotation / RLS contractをdevice側に持つと、攻撃面が増える。
- Chimera API が Supabase service role key を抱えてsession契約を強制するほうが、研究室環境でも本番環境でも管理しやすい。

### Why QR + join token, not OAuth device code

- 展示会場でinternet経由でのpolling前提のdevice code flowは、会場netが脆弱な現場 (ポスターセッション) では不安定。
- QR は印刷物・スマホ画面どちらでも配布でき、presenter自身がjoin token rotation を制御できる (poster再印刷で旧token失効)。
- joinTokenが流出してもsingle-use + 10分でwindow がclose、被害が限定的。

## API contract (client視点)

```http
POST /api/v1/runtime/exchange
Content-Type: application/json
{
  "sessionCode": "ABC123",
  "joinToken":   "eyJhbGciOi...",
  "deviceId":    "uuid-v4 generated by client, persisted in PlayerPrefs",
  "deviceLabel": "Quest 3 / Lab C"
}
→ 200 application/json
{
  "schemaVersion": "1.0",
  "sessionCode":   "ABC123",
  "runtimeToken":  "eyJ...",
  "refreshToken":  "rfsh_...",
  "expiresAt":     "2026-05-07T10:15:00Z",
  "scope":         "session-runtime"
}
→ 401 invalid/expired join token
→ 403 session revoked / device blocked
→ 409 session not yet published

POST /api/v1/runtime/refresh
{ "refreshToken": "rfsh_..." }
→ 200 same shape as exchange
→ 401 refresh expired (client must re-scan QR)

GET /api/v1/runtime/{sessionCode}/manifest
Authorization: Bearer <runtimeToken>
→ 200 RuntimeManifest (existing schema)
→ 401 token expired (client refreshes + retries once)
```

## Consequences

良い点:

- HMD で virtual keyboard を出さずに session join が完結する。
- session scope が短期token に閉じるため、device紛失時のblast radiusが小さい。
- backendは Supabase JWT を内部で扱うだけで、deviceには公開しない。
- 同一device がmulti-sessionに参加してもPlayerPrefs key が衝突しない。
- editor escape hatch (`DebugRuntimeToken`) でauth flow をbypass し、dev iteration速度を保つ。

技術リスク:

- joinToken 単独でsession join できるため、QR の物理セキュリティ (誰が見られる場所にあるか) が前提になる。発表者は印刷QR を session開始直前に貼る運用とする。
- PlayerPrefs (= Android SharedPreferences) は他appからは読めないが、root端末では平文。P1で Android Keystore-backed encryption に差し替える計画。
- joinToken のrotation policyを backend で持つ必要がある。dashboard publish 後に再発行できないと、リハーサル中にtokenが切れて困る。
- camera-based QR scanner (`MetaPassthroughQrScanner`, `XrealQrScanner`) は Phase 2/3 でしか実装されないため、Phase 0/1 は `ManualSessionEntry` で運用する。

## Validation

- `SessionJoinTokenTests` が canonical URI / API override / scheme-host validation / 必須param抜け検出を網羅 (5+ケース、green済)。
- `SessionCredentialsTests` が expiry skew / unknown expiry / local→UTC正規化を網羅 (4ケース、green済)。
- `ManifestClient.FetchAsync(sessionCode, bearer, ct)` が 401 で `ManifestUnauthorizedException` を投げる。
- `ChimeraSession.BootAsync` が `OnAuthRequired` event を fire してから `provider.RequestEntryAsync` を await する。
- `CredentialStore.Save / Load / Clear` が sessionCode-namespaced PlayerPrefs key で round-trip する (Editor / device 上で smoke test)。
- Phase 1 で Quest 3 上で `ManualSessionEntry` 経由で end-to-end (entry → exchange → manifest → cached TTS再生) が回ることを確認する。
