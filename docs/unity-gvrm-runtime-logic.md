# Unity GVRM Runtime Logic

This document defines the Unity-side runtime logic for using human `.gvrm`
avatars generated by the ChimericAvatar web/API pipeline.

The goal is not just to display a Gaussian Splat cloud. The goal is to load a
human Gaussian avatar, align it with a VRM body, and eventually animate the
splats through the VRM skeleton in the same spirit as `naruya/gaussian-vrm`.

## 1. Source Model

ChimericAvatar treats `naruya/gaussian-vrm` as the upstream reference for the
human avatar logic.

Key upstream assumptions:

- `.gvrm` is a ZIP bundle containing:
  - `model.vrm`
  - `model.ply`
  - `data.json`
- `data.json` stores binding metadata:
  - `modelScale`
  - `boneOperations`
  - `gsPosition`
  - `gsQuaternion`
  - `splatVertexIndices`
  - `splatBoneIndices`
  - `splatRelativePoses`
- The human Gaussian splats follow an underlying skinned VRM mesh.
- For performance, the upstream web implementation avoids sorting fully skinned
  splat positions every frame. It groups splats into sub-scenes and uses static
  positions for sorting while using skinned positions for rendering.

Important references:

- Upstream repository: https://github.com/naruya/gaussian-vrm
- Project explanation: https://gaussian-vrm.github.io/
- Paper: https://arxiv.org/abs/2510.13978
- Unity splat renderer reference: https://github.com/aras-p/UnityGaussianSplatting
- VR-capable Unity splat reference: https://github.com/ninjamode/Unity-VR-Gaussian-Splatting

## 2. Existing Unity Runtime Assets

The Unity runtime already has the low-level data loaders:

```text
apps/xr-client/Assets/ChimeraRuntime/Runtime/Avatar/
  GvrmZipReader.cs        .gvrm ZIP reader and validator
  PlyParser.cs            PLY header parser
  GaussianSplatStream.cs  typed 3DGS PLY stream reader
  GvrmBoneBatches.cs      splatBoneIndices -> contiguous per-bone ranges
  DefaultVrmLoader.cs     UniVRM-gated VRM loader / fallback primitive

apps/xr-client/Assets/ChimeraRuntime/Runtime/Manifest/
  GvrmMetadata.cs         DTO for data.json
```

Do not duplicate these responsibilities in the renderer. The renderer should
consume `GvrmBundle`, `GaussianSplatStream`, `GvrmMetadata`, and
`GvrmBoneBatches`.

## 3. Runtime Milestones

### Milestone A: Static Human GVRM

Purpose:

Validate that Unity can read the same `.gvrm` that the web preview downloads and
place the Gaussian human in the same coordinate frame as the VRM.

Required behavior:

1. Load `.gvrm` via `GvrmZipReader.Load`.
2. Parse `model.ply` via `GaussianSplatStream.Read`.
3. Load `model.vrm` via `DefaultVrmLoader` / UniVRM.
4. Apply `metadata.ModelScale` to the VRM root.
5. Render all splats using their raw PLY position, transformed by:

```text
worldPosition =
  AvatarRoot
  * VRM/GVRM scene transform
  * TRS(metadata.gsPosition, metadata.gsQuaternion, 1)
  * plyPosition
```

Pass condition:

- Human splat cloud appears at the correct scale and orientation.
- It overlaps the loaded VRM body closely enough to debug alignment.
- Quest/XREAL does not need animation yet.

This is equivalent to the dashboard's static preview path and is the first
smoke test for every `.gvrm`.

### Milestone B: Bone-Grouped Human GVRM

Purpose:

Prepare the data layout for animation without updating every splat on CPU.

Required behavior:

1. Build `GvrmBoneBatches` from `metadata.SplatBoneIndices`.
2. Reorder GPU splat buffers by `PermutedSplatIndices`.
3. Build one `SplatBoneRange` table:

```text
boneIndex -> start/count in reordered splat buffer
```

4. Store original splat index or remapped metadata index when needed for lookup.

Pass condition:

- Static rendering still matches Milestone A.
- Splats are grouped by bone in GPU buffers.
- Debug mode can color splats by bone.

Rationale:

Naruya's web runtime groups splats into sub-scenes so sorting can stay tractable.
Unity should follow the same idea, but implement it as contiguous GPU buffer
ranges instead of many GameObjects.

### Milestone C: Skinned Human GVRM

Purpose:

Animate the human splats with the VRM skeleton.

Required behavior:

For each splat `i`, use:

```text
vertexIndex = splatVertexIndices[i]
relativePos = splatRelativePoses[i]
```

At runtime:

```text
meshVertexRest      = bodyMesh.vertices[vertexIndex]
meshVertexSkinned   = skin(bodyMesh, vertexIndex, currentBones)
relativePosSkinned  = rotate relativePos by the delta from rest skinning to current skinning
splatCenterSkinned  = meshVertexSkinned + relativePosSkinned
```

Implementation rule:

- Do not calculate this per splat on C# CPU every frame.
- Use GPU buffers and compute shader or vertex shader logic.

Recommended GPU buffers:

```text
SplatInputBuffer
  raw position xyz
  raw scale xyz/log scale
  raw rotation xyzw
  opacity
  SH/color coefficients

SplatBindingBuffer
  vertexIndex
  boneIndex
  relativePose xyz

MeshBindingBuffer
  rest vertex position
  normal
  skin indices
  skin weights

BoneMatrixBuffer
  current bone matrices
  rest bone matrices or inverse bind matrices

SplatOutputBuffer
  skinned center xyz
  transformed covariance / rotation data as needed
```

Pass condition:

- A simple arm / head / torso animation moves the splats with the VRM.
- No full CPU-side splat position array rewrite occurs per frame.
- Sorting remains stable enough for a human avatar at normal viewing distance.

## 4. Coordinate System Notes

The `.gvrm` produced by the web/API pipeline already includes alignment fields:

```json
{
  "modelScale": 1.0,
  "gsPosition": [0, 0, 0],
  "gsQuaternion": [0, 0, 1, 0]
}
```

Unity must not invent a second alignment path. Use the metadata first.

Rules:

- `modelScale` scales the VRM body.
- `gsPosition` and `gsQuaternion` place the Gaussian scene relative to the VRM.
- `splatRelativePoses` are already in the binding frame emitted by the server.
- `_serverBoneNames` may be present in API-built `.gvrm`; use it for robust bone
  remapping if Unity skeleton bone order differs from the server.

If the avatar appears mirrored, upside-down, or offset:

1. Verify `gsQuaternion` is applied in the same component order used by Unity
   (`x, y, z, w`).
2. Verify VRM 0.x coordinate correction from UniVRM is not applied twice.
3. Verify `modelScale` is applied to the VRM root, not to the splat buffer alone.
4. Compare against dashboard static preview using the same downloaded `.gvrm`.

## 5. Renderer Architecture

Recommended classes:

```text
GvrmAvatarRuntime : MonoBehaviour
  - owns lifecycle
  - subscribes to ChimeraSession.OnGvrmLoaded
  - loads VRM
  - creates StaticGvrmRenderer or SkinnedGvrmRenderer

StaticGvrmRenderer
  - converts GaussianSplatStream to GPU asset/buffers
  - applies gsPosition/gsQuaternion
  - renders all splats without animation

SkinnedGvrmRenderer
  - builds GvrmBoneBatches
  - uploads splat + binding + mesh + bone buffers
  - updates bone matrices each frame
  - dispatches compute shader or draws with shader skinning

GvrmDebugView
  - color by bone
  - show VRM mesh/capsules
  - show splat count, visible splat count, memory estimate
```

Recommended renderer backend:

- Start from `aras-p/UnityGaussianSplatting` concepts for PLY import, GPU sorting,
  and shader layout.
- Keep the ChimericAvatar `.gvrm` loading layer separate from any imported
  package so the app can swap renderer backend later.

## 6. Quest / XREAL Performance Policy

Targets:

```text
Quest 3:
  initial human splat target: 80k - 150k splats
  stretch target: 300k - 400k splats with proper XR settings

XREAL + Beam Pro:
  initial target: 50k - 100k splats
  prioritize stable frame pacing over maximum splat count
```

Rules:

- Use Android Vulkan.
- Use URP.
- Use Single Pass Instanced / Multiview where supported.
- Avoid one GameObject per bone if it creates many renderer state changes.
- Avoid CPU sorting every frame.
- Avoid CPU skinning for all splats every frame.
- Keep static preview available as a fallback mode.
- Provide quality levels:
  - `Preview`: lower splat cap, static or reduced update rate
  - `Presentation`: target stable XR frame rate
  - `Quality`: desktop/editor validation, not default on standalone XR

Expected bottlenecks:

- Depth sorting.
- Overdraw when close to the avatar.
- Large splat screen-space radius near the camera.
- Duplicate stereo rendering if XR single-pass path is not enabled.
- Buffer upload churn if per-frame data is rebuilt on CPU.

## 7. Data Validation

Before rendering:

```text
metadata.splatVertexIndices.Count == splatStream.Count
metadata.splatBoneIndices.Count == splatStream.Count
metadata.splatRelativePoses.Count == splatStream.Count * 3
model.vrm starts with glTF magic
model.ply is binary_little_endian
PLY has x/y/z, opacity, scale_0..2, rot_0..3
```

If validation fails:

- Do not silently render a broken avatar.
- Show a clear error in Unity logs.
- Fall back to default VRM only if presentation must continue.

## 8. Test Plan

EditMode tests:

- `.gvrm` ZIP read.
- PLY header parse.
- Gaussian stream parse.
- metadata count validation.
- bone batch grouping.
- `_serverBoneNames` remapping.

PlayMode tests:

- Load fixture `.gvrm`.
- Static splat render creates GPU buffers and draws nonzero splats.
- VRM root scale matches `modelScale`.
- `gsPosition/gsQuaternion` transform is applied.
- Simple humanoid animation changes bone matrices.
- Skinned renderer updates output buffer without C# per-splat rewrite.

Device smoke tests:

```text
Quest 3:
  80k splats static
  80k splats skinned idle animation
  poster anchor + avatar + captions

XREAL:
  50k splats static
  poster anchor + avatar placement
  presentation mode with captions
```

## 9. Implementation Order

1. `GvrmAvatarRuntime` subscribes to `ChimeraSession.OnGvrmLoaded`.
2. `StaticGvrmRenderer` renders `GaussianSplatStream` with metadata transform.
3. Add debug color-by-bone using `GvrmBoneBatches`.
4. Add VRM load/overlay and verify scale/alignment.
5. Add GPU buffers for binding metadata.
6. Add compute/vertex shader skinning for splat centers.
7. Add XR quality settings and splat caps.
8. Add Quest 3 device benchmark.
9. Add XREAL device benchmark.

## 10. Non-Goals For First Unity Pass

- Do not implement full facial expression deformation first.
- Do not implement dynamic re-authoring or rebuild in Unity.
- Do not support arbitrary multi-character `.gvrm` first.
- Do not optimize for desktop-only million-splat scenes before the human XR path.
- Do not mutate the `.gvrm` file in Unity; treat it as a downloaded runtime asset.
